
# Backend – проверка пакета документов на субсидию

Заготовка для кейса «Агентство инноваций» на хакатоне Сбера. Java, Spring Boot 4.1.1, Gradle, REST API.

## Запуск

Для сборки используйте JDK 26 (совместим с Gradle 9.6 из проекта). Укажите `JAVA_HOME` на ваш JDK.

### IntelliJ IDEA: запуск через Main

1. Клонируйте этот репозиторий и откройте его корневую папку (с `settings.gradle` и `build.gradle`) как Gradle-проект.
2. Выберите установленный JDK 26 для Project SDK и Gradle JVM. Дождитесь завершения синхронизации Gradle: IDEA загрузит зависимости Spring и создаст модуль `SberCase.main`.
3. Выберите общую конфигурацию **Backend Main** и нажмите Run или Debug. Также можно запускать `main()` в `src/main/java/org/example/Main.java` кнопкой рядом с методом.

Конфигурация хранится в `.run/Backend Main.run.xml` и входит в репозиторий; локальные пути к JDK в ней не используются. Docker и PowerShell-скрипты для этого запуска не нужны.

Если IDEA запускает Java без classpath, проверьте, что Gradle синхронизирован, а в конфигурации запуска выбран модуль `SberCase.main`. Если порт 8080 занят, остановите предыдущий экземпляр приложения либо задайте переменную окружения `PORT=8081` в конфигурации запуска.

### Терминал

Выполняйте команды из корня клонированного репозитория:

```powershell
.\gradlew.bat test bootJar
.\gradlew.bat bootRun
```

Linux/macOS: `sh ./gradlew test bootJar`, затем `sh ./gradlew bootRun`.

Сервис: http://localhost:8080. Health: `GET /actuator/health`.

Порт задаётся переменной окружения `PORT`. Собранный JAR: `build/libs/backend.jar`.

```sh
docker build -t subsidy-backend .
docker run --rm -p 8080:8080 subsidy-backend
```

При запуске AI-модуля в Docker необходимо отдельно настроить доступ контейнера к Ollama через `OLLAMA_URL`. Адрес `127.0.0.1` внутри контейнера не указывает на хостовый компьютер.

## Авторизация (Keycloak)

Если задан JWKS, `/api/**` принимает только JWT от Keycloak (`Authorization: Bearer …`) с realm-ролью `specialist` или `admin`:

| Переменная | Пример |
|---|---|
| `SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_JWK_SET_URI` | `http://keycloak:8080/kc/realms/subsidy/protocol/openid-connect/certs` |
| `SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_ISSUER_URI` | `http://localhost/kc/realms/subsidy` – issuer из токена |
| `SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_AUDIENCES` | `subsidy-backend` |

Проверяются подпись, срок действия, issuer и audience. Без токена – `401`, без нужной роли – `403`, оба в формате Problem Details.

Проверка `exp`/`nbf` допускает расхождение часов до 30 секунд. Каждый действующий access token, включая выпущенный через refresh token, проверяется независимо; серверная сессия и привязка к значению токена отсутствуют. Продление frontend выполняет напрямую в Keycloak.

При заданном JWKS необходимо задать issuer; audience по умолчанию `subsidy-backend`. Ошибки `401`/`403` содержат русский `detail`.

`/actuator/health` и `/actuator/info` открыты. Без JWKS API закрыт с `503`; открытый локальный режим требует явного профиля `dev` (`SPRING_PROFILES_ACTIVE=dev`).

`/admin/**` требует `admin`, заявки, оригиналы, проверки и решения – `specialist`. Роль `admin` сама по себе доступа к заявкам не даёт. Справочники доступны обеим ролям. Очередь заявок общая для специалистов; отказы доступа записываются в журнал.

При настроенном Keycloak AI API также требует JWT с подходящей ролью и ключ `X-Api-Key`.

## API заявок

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/document-types` | Доступные типы документов |
| GET | `/api/v1/programs` | Демонстрационный каталог программ |
| POST | `/api/v1/applications` | Создать заявку |
| GET | `/api/v1/applications` | Список заявок |
| GET | `/api/v1/applications/{id}` | Заявка, документы и последний отчёт |
| POST | `/api/v1/applications/{id}/documents` | Multipart: `file`, необязательный `type`; фоновое распознавание |
| PATCH | `/api/v1/applications/{id}/documents/{documentId}` | Исправить поля или тип документа |
| POST | `/api/v1/applications/{id}/documents/{documentId}/reprocess` | Повторить обработку после `FAILED` |
| GET | `/api/v1/applications/{id}/journal` | Журнал обработки и ручных правок |
| GET | `/api/v1/applications/{id}/documents/{documentId}/preview` | Office-просмотр: сначала `202`, затем HTML |
| POST | `/api/v1/applications/{id}/decision` | Сохранить решение специалиста |
| GET | `/api/v1/applications/{id}/documents/{documentId}` | Скачать документ |
| DELETE | `/api/v1/applications/{id}/documents/{documentId}` | Удалить документ |
| POST | `/api/v1/applications/{id}/check` | Проверить комплектность |

Создание заявки:

```json
{
  "programCode": "INNOVATION"
}
```

Пример сценария (bash; в PowerShell вызывайте `curl.exe`):

```sh
curl -X POST http://localhost:8080/api/v1/applications \
  -H 'Content-Type: application/json' \
  -d '{}'

curl -X POST http://localhost:8080/api/v1/applications/UUID/documents \
  -F 'type=APPLICATION' -F 'file=@application.pdf'

curl -X POST http://localhost:8080/api/v1/applications/UUID/check
```

Замените `UUID` на `id` созданной заявки. Обязательные типы определяет выбранная программа; актуальный перечень возвращает `/api/v1/programs`. При настроенном Keycloak добавьте заголовок `Authorization: Bearer <access token>`.

Ошибки возвращаются в формате Problem Details (`application/problem+json`). Ошибки API заявок содержат понятное описание на русском языке.

Файл: до 50 MiB; форматы по расширению: PDF, DOC, DOCX, XLS, XLSX, TXT, PNG, JPG, JPEG.

При загрузке в заявку фактическое содержимое и MIME-тип не проверяются. Скачивание выполняется как двоичный attachment.

До 100 заявок, 20 документов на заявку и 50 MiB файлов суммарно для одного процесса.

### Реквизиты и обработка

При создании принимается только необязательный `programCode`: `{}` и `{"programCode":null}` тоже возвращают `201`.

Организация, ИНН, проект и сумма первоначально равны `null`. Они извлекаются из первого загруженного заявления (`APPLICATION`); источник, уверенность и история ручной правки доступны в `requisites`. Удаление заявления или изменение его типа пересчитывает карточку.

Загрузка сразу возвращает `201` и `processingStatus: "UPLOADED"`. Последовательно работающая очередь запускает классификацию и извлечение через Ollama; при занятой модели документ ждёт.

Перечитывайте заявку до `DONE` или `FAILED`. При ошибке `processingError` содержит причину на русском; повторную обработку можно запустить через `/reprocess`.

Для этого сценария `X-Api-Key` не требуется: доступ регулируется общей авторизацией API заявок. Ollama и модель должны быть доступны серверу Backend.

Нераспознанные поля имеют `value: null` и `status: "NOT_RECOGNIZED"`; подстановка демонстрационных значений не выполняется.

Денежные значения возвращаются числами, даты – в формате `YYYY-MM-DD`. Низкая уверенность распознавания даёт предупреждение в отчёте.

Пример ручной правки:

```json
{
  "fields": [
    {
      "name": "requested_amount",
      "value": 900000
    }
  ]
}
```

Также доступна правка типа документа:

```json
{
  "type": "GUARANTEE_LETTER"
}
```

`originalValue` сохраняет значение до первой правки; `correctedBy` берётся из `preferred_username` проверенного JWT. Без Keycloak используется «Специалист».

Ручное изменение типа сохраняет предложение модели в `detectedType`. Правки записываются в журнал и сбрасывают предыдущий отчёт. Ручные значения сохраняются при завершении фоновой обработки и повторном распознавании.

Проверка возвращает `PROCESSING`, пока документы обрабатываются. Арифметика и сверка сумм выполняются только на распознанных числах: отсутствие значения даёт `WARNING`, а не успешную проверку.

Каждое замечание содержит `severity`, `documentId` и `field` для перехода к источнику.

### Программы, правила и решения (FE-01…FE-06)

Отчёт возвращает явные `PASSED`, `ATTENTION`, `ERRORS` или `PROCESSING`.

Документ после проверки имеет `outcome` из того же набора итогов (`PASSED`, `ATTENTION`, `ERRORS`); до проверки итог равен `null`.

Ошибка обработки или неизвестный тип не дают успешного результата. Любое изменение документов сбрасывает отчёт и итоги файлов. Замечания содержат также `rule` – код правила.

Комплектность вычисляется по выбранной или распознанной программе. Неопределённая программа даёт предупреждение.

`REQUIRED` нужен всегда; `CONDITIONAL` содержит понятное человеку `condition` и код `conditionAttribute` из `/api/v1/application-attributes` (`requiresCertification`, `usesWaterArea`).

Специалист задаёт атрибуты через `PATCH /api/v1/applications/{id}` с `{"attributes":{"requiresCertification":true}}`.

`true` требует документ, `false` исключает его из перечня, `null` или отсутствие дают `CONDITIONAL_UNKNOWN`. Изменение атрибутов сбрасывает отчёт. Дополнительные типы отмечаются `EXTRA`.

Администратор может читать, создавать и изменять программы через `/api/v1/admin/programs` (`GET`, `POST`, `PUT /{code}`) и читать или изменять правила через `/api/v1/admin/rules` (`GET`, `PUT /{code}`).

В режиме Keycloak требуется роль `admin`.

Правила поддерживают включение, строгость и типы документов; параметры: уверенность (`threshold`), допуск по суммам (`tolerance`), минимальная доля собственных средств (`minOwnFundsShare`, 0..1), предупреждение о сроке действия (`daysBeforeExpiry`).

Изменения применяются при следующей проверке.

При первой инициализации создаются INNOVATION, BEACH и MODERNIZATION с перечнями документов из кейса; минимальная доля собственных средств – 0.5.

Проверка подписей остаётся ручной и по умолчанию даёт `ATTENTION`.

При `PUT` передавайте полученную `version`: устаревшая или отсутствующая версия возвращает `409`. `updatedBy` и `updatedAt` назначает сервер.

`paramSchema` задаёт единицы, границы и обязательность параметров; проценты вводятся в интерфейсе как 0..100, но API принимает долю 0..1.

Изменения настроек и аудит записываются в БД одной транзакцией. Проверка использует снимок настроек на момент запуска; готовые отчёты не пересчитываются сами.

`/api/v1/admin/journal?limit=200&before=<ISO instant>&action=PROGRAM_UPDATED` объединяет события заявок и настройки администратора: новые первыми, `before` строго исключительный.

Изменения содержат `before`, `after`, `version`, `objectType`, `objectId`.

Решение: `POST /applications/{id}/decision` с `{"decision":"RETURNED","comment":"Дослать документы"}`.

Возможны `ACCEPTED`, `RETURNED`, `REJECTED`; для возврата или отклонения комментарий обязателен.

Автор берётся из JWT. Решение хранится отдельно от автоматического отчёта и сохраняется при его сбросе.

Без готового отчёта или во время обработки решение возвращает `409`. Повторное решение сохраняет прежнее и новое значения в журнале.

Данные сохраняются в файловой БД H2: `STORAGE_JDBC_URL` по умолчанию `jdbc:h2:file:./data/subsidy`.

Заявки, оригиналы, реквизиты, отчёты, решения, настройки и журналы переживают перезапуск.

В Compose каталог `/app/data` подключён к volume `backend-data`; не удаляйте volume при обновлении.

Прерванная обработка после перезапуска получает `FAILED` и допускает повторный запуск. БД рассчитана на один экземпляр Backend.

DOC/DOCX/XLS/XLSX доступны в статическом HTML-просмотре: текст Word и таблицы Excel, со встроенными стилями и экранированием содержимого; изображения и исходная вёрстка Office не воспроизводятся.

Первый запрос `/preview` возвращает `202` с `Retry-After: 3`; готовый – `200 text/html`, повреждённый – `422` с русским описанием.

Конвертация работает в отдельном процессе с ограничениями памяти и времени, не выполняет макросы и формулы.

Оригинал остаётся доступен для скачивания. Доступ требует той же роли, что и чтение документа.

Фоновое задание ограничено 240 секундами (`DOCUMENT_PROCESSING_TIMEOUT_SECONDS`, 1..600).

По истечении времени документ получает `FAILED`; очередь продолжает обработку следующих файлов. Запрос повторной обработки записывается в журнал как `DOCUMENT_REPROCESS_REQUESTED`.

## AI-модуль анализа документов

Модуль `org.example.subsidy.ai` обеспечивает классификацию документов, OCR и извлечение реквизитов с использованием локальной мультимодальной модели Qwen3-VL через Ollama.

Модуль не принимает решение о выдаче субсидии и не проверяет комплектность пакета. Бизнес-правила, сопоставление документов и принятие решений выполняются основным Backend.

### Интеграция с Backend

Для использования отдельного AI-сервиса задайте:

| Переменная | Назначение |
|---|---|
| `AI_REMOTE_URL` | Полный URL `/api/v1/ai/analyze` |
| `AI_REMOTE_API_KEY` | Ключ доступа к AI API длиной не менее 32 символов |

Основной Backend отправляет документ на указанный адрес и преобразует ответ AI к своему контракту. При отсутствии `AI_REMOTE_URL` используется предусмотренное основным Backend прямое взаимодействие с Ollama.

Отдельный AI endpoint возвращает `needs_review`, `warnings` и `uncertain_fields`.

Итоговые статусы проверки заявки `PASSED`, `ATTENTION` и `ERRORS` рассчитываются основным Backend независимо от этого признака.

### Поддерживаемые типы документов

| Тип | Описание |
|---|---|
| `APPLICATION` | Заявление на субсидию |
| `PERSONAL_DATA_CONSENT` | Согласие на обработку персональных данных |
| `CONFORMITY_CERTIFICATE` | Сертификат соответствия |
| `PROJECT_PRESENTATION` | Презентация проекта |
| `COST_JUSTIFICATION` | Обоснование затрат |
| `BANK_STATEMENT` | Банковская выписка или справка |
| `REAL_ESTATE_DOCUMENT` | Документ на недвижимость, выписка ЕГРН |
| `GUARANTEE_LETTER` | Гарантийное письмо |
| `UNKNOWN` | Тип не определён |

Для каждого типа документа применяется собственная схема извлечения.

Основные возможности:

- Распознавание организации или ИП, ИНН, ОГРН/ОГРНИП, КПП.
- Извлечение даты, подписанта, суммы и назначения субсидии.
- Извлечение банковского владельца, массива счетов и остатков.
- Структурированные паспортные данные: серия, номер, орган выдачи, дата выдачи.
- Извлечение кадастрового номера, площади, назначения, адреса и правообладателя.
- Обработка сертификатов, гарантийных писем, презентаций и обоснований затрат.
- Проверки формата и контрольных цифр ИНН, формата КПП, дат и денежных сумм.
- Разделение диагностических предупреждений и ошибок, требующих ручной проверки.

Отсутствующие реквизиты возвращаются как `null`. Недостающие сведения не подменяются значениями из других документов.

### Поддерживаемые форматы

- PDF с текстовым слоем.
- Сканированные PDF.
- DOCX.
- TXT в UTF-8.
- PNG.
- JPG и JPEG.

Текст PDF извлекается с помощью Apache PDFBox. Изображения анализируются Qwen3-VL.

Длинные документы обрабатываются фрагментами с последующим объединением реквизитов. Классификация выполняется отдельно от извлечения.

Для заявлений предусмотрено дополнительное извлечение запрашиваемой суммы из бюджетной таблицы с учётом порядка столбцов и итоговой строки.

Для банковских справок поддерживаются несколько счетов с отдельными остатками.

### Технические ограничения

- Входной файл отдельного AI-модуля: до 20 МиБ.
- PDF: до 30 страниц.
- Извлечённый текст: до 64 000 символов.
- Фрагмент текста для модели: до 4000 символов.
- Изображения PDF: до двух страниц в одном анализе.
- Отдельная обработка изображений, встроенных в DOCX, не реализована.
- Несколько JPG пока нельзя отправить как один многостраничный документ.
- При остановке генерации с `done_reason=length` выполняется повторная попытка с лимитом 3072 токена вместо 1536.

Лимиты Spring multipart настраиваются отдельно и не должны быть меньше лимита AI-модуля.

Самостоятельный AI endpoint не поддерживает DOC, XLS и XLSX. Наличие этих форматов в API заявок не означает их поддержку в `/api/v1/ai/analyze`.

### Установка и настройка

Установите Ollama и загрузите модель:

```powershell
ollama pull qwen3-vl:4b-instruct
```

Переменные окружения:

| Переменная | Назначение |
|---|---|
| `AI_API_KEY` | Ключ доступа к AI API, минимум 32 символа |
| `OLLAMA_URL` | Адрес Ollama, по умолчанию `http://127.0.0.1:11434` |
| `OLLAMA_MODEL` | Модель, по умолчанию `qwen3-vl:4b-instruct` |

В IntelliJ IDEA переменные задаются в Run Configuration.

При стандартной локальной конфигурации документы не отправляются в облачные AI API.

Если `AI_API_KEY` отсутствует или имеет недопустимую длину, самостоятельный AI API возвращает `503 Service Unavailable`.

### HTTP API

**`POST /api/v1/ai/analyze`**

- Запрос: `multipart/form-data`.
- Поле файла: `file`.
- Авторизация: `X-Api-Key`.
- При настроенном Keycloak дополнительно применяется JWT-авторизация.
- Ответ: JSON.

Пример PowerShell:

```powershell
$key = Read-Host "AI API key"
$file = "C:\Documents\application.pdf"

curl.exe -sS -X POST "http://localhost:8080/api/v1/ai/analyze" `
    -H "X-Api-Key: $key" `
    -F "file=@$file"
```

При ошибках возможны ответы:

| HTTP | Причина |
|---|---|
| `401` | Неверный API-ключ |
| `413` | Превышен лимит загрузки |
| `422` | Файл не может быть обработан |
| `502` | Некорректный результат AI |
| `503` | AI-сервис недоступен или занят |
| `504` | Превышено время ожидания |

### Формат ответа

Пример ответа банковской справки с синтетическими данными:

```json
{
  "document_type": "BANK_STATEMENT",
  "fields": {
    "organization": "Иванов Иван Иванович",
```

### Предупреждения и ручная проверка

AI-модуль разделяет замечания на критичные и диагностические.

Критичные замечания:

- Неизвестный тип документа.
- Отсутствие обязательного реквизита.
- Некорректный формат ИНН, КПП, даты, денежной суммы или номера банковского счёта.
- Некорректные паспортные реквизиты.
- Истёкший срок сертификата.
- Неоднозначность критичной суммы, банковских счетов, кадастрового номера и других критичных реквизитов.
- Очевидное смешивание правообладателя недвижимости с органом, выдавшим ЕГРН.

Диагностические замечания:

- Неуверенность модели в названии проекта, его описании или других некритичных полях.
- Неуверенность в корректно сформатированных реквизитах, которые нельзя подтвердить дополнительной проверкой.
- Неподтверждённый необязательный ИНН клиента банка.

Критичные замечания устанавливают `needs_review: true`.

Диагностические замечания сохраняются в `warnings` и `uncertain_fields`, но сами по себе не устанавливают `needs_review: true`.

`needs_review` не является числовой вероятностью правильности распознавания. Qwen3-VL не предоставляет калиброванный показатель уверенности, поэтому AI-модуль не рассчитывает фиктивные проценты достоверности.

Если серия и номер паспорта ошибочно определены моделью как ИНН, совпадающее значение ИНН исключается из результата.

Неподтверждённый ИНН банковского клиента также не выдаётся за достоверный.

`needs_review: false` не является подтверждением подлинности документа, достоверности всех значений или права заявителя на субсидию.

### Отличие AI-проверки от проверки заявки

Основной Backend использует собственное правило `LOW_CONFIDENCE`.

Исходное значение порога – `0.8` (80%). Оно управляется настройками правил Backend.

Также действует самостоятельное правило `MANUAL_REVIEW_REQUIRED`, связанное с проверкой подписей и соответствия регламенту специалистом.

Поэтому возможна ситуация:

- AI вернул `needs_review: false`.
- Основной Backend вернул `ATTENTION`.

Это не противоречие: AI оценивает результат извлечения, а Backend применяет бизнес-правила к заявке.

Снижение порога `LOW_CONFIDENCE` не отменяет остальные проверки.

### Безопасность

- Разбор документов выполняется в отдельном Java-процессе с ограничениями памяти и времени.
- Ограничиваются размеры входных файлов, изображений, количество страниц PDF и объём распакованных данных.
- Число одновременно выполняемых анализов ограничено.
- Запросы к Ollama имеют тайм-ауты.
- Инструкции внутри документа считаются недоверенными данными.
- Защита от prompt injection не гарантирует абсолютную устойчивость.
- API-ключ не шифрует трафик. При доступе через недоверенную сеть необходим HTTPS или защищённый туннель.
- Паспортные и другие персональные данные не следует записывать в журналы диагностики.
- Для автоматических тестов используются синтетические данные.
- Дочерний процесс парсинга не является полноценной песочницей операционной системы.

### Тестирование

Запуск тестов:

```powershell
.\gradlew.bat clean test
```

Для ручной проверки используются открытые пакеты документов хакатона.

На открытых образцах проверялись классификация, извлечение реквизитов заявлений, сумм бюджетных таблиц, банковских счетов и паспортных данных.

Точность на закрытых документах не гарантируется.

## Границы заготовки

Перечень документов демонстрационный, а не официальный регламент субсидии.

Проверка выявляет недостающие типы, дубликаты и ошибки значений. Недостающий обязательный документ даёт `ERRORS`, ручная проверка – `ATTENTION`.

Решение об одобрении принимает специалист отдельно.

После загрузки, удаления или ручной правки документа предыдущий отчёт сбрасывается.

Обнаруженные арифметические ошибки дают `ERRORS`, если правило настроено со строгостью `ERROR`.

Данные заявок и загруженные оригиналы сохраняются в файловой БД H2 в предусмотренной конфигурации хранения. БД рассчитана на один экземпляр Backend.

Авторизация `/api/**` выполняется через Keycloak при заданном JWKS. AI API дополнительно защищён ключом `X-Api-Key`.

Для демонстрации используйте синтетические документы.

AI-анализ интегрирован с обработкой заявок. Проверка подлинности подписей остаётся задачей специалиста.

Для дальнейшей работы необходимо уточнить официальный регламент и провести испытания на независимом наборе документов.

GitHub Actions запускает тесты и сборку на push/PR.
